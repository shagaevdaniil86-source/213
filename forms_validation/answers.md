# ПР7 Ответы на вопросы

## 1. Какие HTML5-атрибуты используются для клиентской валидации и какую функциональность они предоставляют?

required требует значения, minlength/maxlength ограничивают длину, min/max/step — числовой диапазон, pattern — шаблон всей строки, type=email — формат email. checkValidity() проверяет ограничения программно. Проверка на сервере всё равно нужна в реальном приложении.

## 2. В чем разница между novalidate атрибутом формы и отключением валидации через JavaScript?

novalidate отключает встроенную интерактивную проверку при submit, но не Constraint Validation API. JavaScript может вызвать checkValidity(), настроить setCustomValidity() или установить form.noValidate. preventDefault() отменяет отправку, а не отключает всю валидацию.

## 3. Как правильно связать <label> с полем ввода и почему это важно для доступности?

for у label должен совпадать с уникальным id поля, либо поле вкладывается внутрь label. Это даёт доступное имя и возможность фокусировать поле нажатием на подпись. В форме оба варианта применены.

## 4. Какие типы полей input наиболее подходят для разных видов данных (email, телефон, пароль и т.д.)?

email проверяет формат адреса, tel даёт подходящую мобильную клавиатуру, password скрывает символы, date выбирает дату, number подходит для числовых величин. Телефон не следует хранить как number, поскольку нужны плюс и форматирование.

## 5. Как работает валидация с помощью pattern атрибута и в каких случаях его следует использовать?

pattern задаёт регулярное выражение без разделителей, проверяемое для всего непустого значения. Он полезен для пароля или фиксированного формата. required отдельно запрещает пустое поле. Телефон в работе проверяется собственной функцией.

## 6. Какие события JavaScript используются для реализации валидации в реальном времени и почему?

input вызывается при каждом изменении значения, blur — после ухода фокуса, submit — для финальной проверки. В работе input/blur обновляют сообщения; изменение пароля повторно проверяет подтверждение.

## 7. Как обеспечить доступность сообщений об ошибках для пользователей скринридеров?

Ошибка связана с полем через aria-describedby; aria-invalid сообщает состояние. Контейнер сообщения имеет aria-live, итог — role=status. После неудачного submit фокус перемещается к первому неверному полю. Ошибка выражена текстом, а не только цветом.

## 8. В чем преимущества использования fieldset и legend для группировки полей формы?

fieldset группирует связанные поля, legend задаёт название группы. В работе отдельно выделены личная информация, безопасность, дополнительные данные, пол и интересы. Группа читается как связанная при использовании скринридера.

## 9. Как реализовать кастомную валидацию для сложных случаев (например, подтверждение пароля)?

Подтверждение пароля сравнивается с исходным паролем. Проверка запускается при изменении обоих полей и при submit. Нельзя забывать сброс старой ошибки после исправления. В реальном сервисе пароль повторно проверяется сервером.

## 10. Какие методы CSS используются для визуального отображения состояний валидности/невалидности полей?

Можно использовать :valid/:invalid, :user-valid/:user-invalid, классы и [aria-invalid=true]. Здесь JavaScript выставляет .error/.valid и aria-invalid, CSS задаёт рамку и фон; текстовая ошибка дополняет визуальное состояние.
